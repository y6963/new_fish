## 采访 400 的修复（13:40）

### 关键判定：换模型能不能解决
- 该 400 来自**模型自带 chat template 的规则**，不是推理框架 bug（vLLM issue #41114 已确认 "model template rule, not a vLLM bug"）。
- 主流开源模型（Qwen / Llama / ChatML 系）模板普遍强制「system 只能一条且必须在开头」；**OpenAI 官方 API 反而接受多条 system**。
- 结论：**换模型不可靠**（同端点的开源模型大概率照样失败）。正确做法是客户端保证 messages 规范，别依赖服务端容忍。
- 另有 PR 佐证（next-ai-draw-io #774）：对接 vLLM/LMStudio 时把两条 system 合并为一条即可修复。

### 改动
- 新增 `backend/scripts/oasis_message_patch.py`（模拟子进程专用，无 flask 依赖）：
  - `normalize_messages()`：合并所有 system 为一条并置于 index 0；**以第一条为准**（OASIS 插的截断版在前，记忆里的完整版在后且是其超集 → 保留截断版，正好符合"去掉 # RESPONSE FORMAT"的原意图）；互不包含的多条 system 才拼接。
  - `fold_system_into_user()`：服务端连单条 system 都拒时的降级，折叠进首条 user。

  - 选 `_aget_model_response` 而非 `perform_interview` 作为注入点：一处覆盖 interview / test / 常规 astep 三条路径。

### 追问澄清：换 OpenAI 协议的服务就行吗（13:50）
**关键区分：协议层 ≠ 模板层。**
- 协议层（`/v1/chat/completions` + messages 数组）：所有"OpenAI 兼容"服务都一样，**协议不禁多条 system** → 都收下。
- 模板层：服务端用**模型自带 jinja** 把 messages 渲染成文本，这一层才分胜负。
- Qwen3.5/3.6 真实模板片段（chat_template.jinja 83-86 行）：
  `{%- if message.role == "system" %}{%- if not loop.first %}{{ raise_exception('System message must be at the beginning.') }}`
  → 规则精确含义是「**system 只允许出现在 index 0**」，不是"必须在开头"；第二条 system 无论在哪都拒。
- OpenAI 官方之所以能通过：它不走这层开源模板，内部渲染接受多条 system。
- 所以「支持 OpenAI 协议」这个卖点与本问题无关；决定成败的是背后模型的模板（Qwen/Llama/ChatML 系几乎都拒）。商业中转同理，看背后是谁的模板。

**本地实证方法（无需联网、无需模型权重）**：用 jinja2 手动建 Environment，注入 `raise_exception` 全局函数，渲染上述片段即可复现 400 与通过两种情况。已验证：修复前报 "System message must be at the beginning."，修复后正常渲染出 ChatML。

**服务端备选解法**（若能控制 119.80.249.67 的部署）：给 vLLM 传 `--chat-template` 换成宽松模板（社区有 "Qwen3.5-compatible relaxed" 版本：把所有 system 合并成一个 block）。客户端补丁不依赖服务端，优先用补丁。

### 从代码读出的硬约束（决定结构设计的事实）
- 下游**只吃纯文本**：`ontology_generator.generate(document_texts: List[str])`；`graph_builder.build_graph_async(text, ontology, chunk_size=500, chunk_overlap=50)`。
  结构化信息必须渲染进文本，否则等于没传。
- `zep_cloud/types/batch_add_item.py` 的 `BatchAddItem` **支持 `created_at` 与 `name`，但代码没传**（`graph_builder.py:470`）
  → 旧新闻在图谱里的时间戳是"现在"，舆情演化顺序失真。最高性价比修复点。
- `source_description` 现在是硬编码常量；`metadata` 只放 chunk_index + sha256 → 来源全丢。
- `split_text_into_chunks(500, 50)` 机械切块把不同来源/时间切进同一 chunk，且第 3 块后来源头全丢 → 实体抽取串味。
- 硬限制：单块 ≤10000 字符、单批 ≤350 条、总量 ≤50000 条、`MAX_ONTOLOGY_TYPES=10`。
- `zep_entity_reader` 丢弃只有 Entity/Node 标签的节点 → 本体没覆盖的实体全丢。
- `follower_count=150` 硬编码、用户名后缀 `random.randint(100,999)` → 影响力维度目前是假的。
- `total_simulation_hours` / `hot_topics` / `initial_posts` 全靠 LLM 猜（config_generator:537/648）。

### 设计主张
三层：`SeedPackage` → `EventCluster`（去重簇，30~80）→ `EvidenceItem`（原子证据，300~1500）。
- EvidenceItem 五层字段：归属(source/author/tier/credibility) · 时序(published_at→created_at) · 内容 · 传播(engagement) · 语义预标注(mentioned_entities/stance/claim)。
- 冲突**显式保留**（`claim_conflicts` + `CONTRADICTS` 边），不合并成中立描述——合并会抹掉舆情演化张力。
- `prediction_query.time_horizon` → `total_simulation_hours`；`timeline` → `initial_posts`；`pulse` → `hot_topics`。
- `gaps[]` 显式留白防 LLM 编。
- 零改造对齐本体阶段：每个 EventCluster 渲染成一篇"文档"，`document_index` 即簇号，长文本抽样天然变成按簇分层。
- 分块改"证据驱动"：长文切块时每块重复渲染证据头（1/4、2/4）。

### 分三期落地
M1（半天）：结构化渲染 + 传 `created_at`，不改现有签名。M2（一天）：簇聚合进图谱/本体。M3（一天）：timeline/pulse 直出配置 + 影响力去硬编码。

## 关于"通用性"的最终结论（15:20）

- **系统能力边界（必须向用户讲清）**：MiroFish 模拟的是"这些主体在社媒上怎么说、舆论怎么裂"，
  **不是事件结果本身**。战争预测它答不了"谁赢"，答得了"各方表态如何演化、何时出现分裂"。
  真推演需要额外引擎（兵棋/Lanchester/博弈），社媒模拟只是其中一个输入。
- **缺失的一环是「检索计划」**（search plan），不是 seed 格式：输入一句话 → LLM 拆出
  N 个检索维度 → 每个维度单独检索 → 汇成种子。这才是"各种任务都适用"的关键，且它可以用 LLM
  动态生成，因此不锁领域。**复杂度差异在这一层，不在数据结构层。**
- **硬约束发现**：`ONTOLOGY_SYSTEM_PROMPT` 要求实体"必须能在社媒发声"，明文禁止抽象概念
  → 坦克、兵力、地形这类客观实体进不了图。零侵入解法：把它们作为**发声主体的 attributes**
  挂上去（Zep 实体 attributes 本来就是自由字典），而不是放宽本体。
- 变量配给清单（领域知识载体，与格式无关）：舆情=立场/传播/KOL；市场=份额/营收/增长/资本；
  战争=兵力/装备/补给/地理/经济承受力/外部干预。**种子里没有决定结果的变量，格式再漂亮也是空的。**
