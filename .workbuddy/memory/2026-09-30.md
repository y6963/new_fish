## 调试报 "No module named xxx" 的根因（已实测 + 已修配置）

**项目是 editable 安装的**：`backend/.venv/lib/python3.12/site-packages/_editable_impl_mirofish_backend.pth`
内容就一行 `/home/A/ysy/fish/backend`，把这个路径永久钉进了 **该 venv 的** sys.path。

两个推论：
1. 依赖只在 `backend/.venv` 里。实测系统 `python3 -c "import flask"` → ModuleNotFoundError，
   venv 里 flask 3.1.2 + zep_cloud 均正常。
   → **运行时不报错、按 F5 却报包缺失 = IDE 用了另一个解释器**，跟依赖装没装无关。
2. `import app.xxx` 与 cwd 无关（因为 .pth），所以"找不到包"**不可能**是工作目录问题。
   反过来：用错解释器时改 cwd 也救不回来。

已修两处配置：
- 新建 `.vscode/settings.json`：`python.defaultInterpreterPath` + `python.analysis.extraPaths`（让 Pylance
  认识 `app`），并用 `windows/linux/osx` 平台键区分路径（Windows 是 `.venv/Scripts/python.exe`）。
- 改 `.vscode/launch.json`：原先第 1 项「当前文件」**既没指定 python 也没指定 cwd**，
  是最容易踩的一项；现在 5 个配置全部显式带 `python + cwd + justMyCode:false`，并各加 `windows.python` 覆盖。

排错三句（让用户能自己定位）：

| 场景 | 命令 | 期望 |
|---|---|---|
| 终端实际跑的 | `python -c "import sys,flask;print(sys.executable)"` | 路径指向 backend/.venv |
| IDE 正在用的 | 右下角状态栏 / Ctrl+Shift+P → Python: Select Interpreter | 同上 |
| 确认 | 显式用 `backend/.venv/bin/python script.py` 跑 | 不报错 = 就是解释器选错 |

## 调试时的前后端启动顺序（已写进 README_debug.md）

`package.json` 的启动链路：
- 后端 `npm run backend` = `cd backend && uv run python run.py` → **uv 自动激活 venv，所以运行时从不缺包**，
  但也因此在 5001 上跑起来的进程**没挂 debugpy，断点命中不了**。
- 前端 `npm run frontend` = `cd frontend && npm run dev` = `vite --host`，端口 **3000**，
  `vite.config.js` 里 proxy `/api` → `http://localhost:5001`。
- `npm run dev` = concurrently 一次起俩，**调试时必须拆成两步单独起**。

结论：**浏览器永远开 3000**（5001 只回 JSON）。调试标准顺序 = F5 选「1. Flask 后端」→ 另开终端起前端。

⚠️ **前端命令按目录区分**（用户已踩坑：在 `frontend/` 里敲 `npm run frontend` → `Missing script`）：
- 在 `frontend/` → `npm run dev`
- 在根目录 → `npm run frontend`（内部即 `cd frontend && npm run dev`）
`frontend` 这个脚本名**只存在于根 package.json**。文档已改成默认推荐 `cd frontend && npm run dev`。
坑：`.env` 里 `FLASK_DEBUG=true` 会让 Flask 开 reloader 派生子进程 → 断点漂到子进程表现为"停不下来"
（`Config.DEBUG` 读 `FLASK_DEBUG`，默认 False）。改 Python 要重启后端，改 Vue 保存即生效。

## 概念辨析：「四层记忆」这个说法其实用宽了（14:20 用户质疑）

用户指出：这些环节看起来就是系统运行流程的每一步，凭什么叫"记忆"？
**这个质疑成立，以后讲这段要按下面的定性说，别再一律叫"记忆"。**

判定标准两条（讲的时候先给标准再判）：
1. **跨时间保留**（不是用完就丢）
2. **会反过来改变后来的行为**（不只是被读出来展示）

| 层 | 定性 | 判定 |
|---|---|---|
| 对话历史（camel ChatHistoryMemory，进程内存） | **唯一的真记忆** | ①✓ ②✓ |
| 人设卡（CSV/JSON） | **出厂设定 / 身份** | ①✓ ②✗（全程不变，不受经历影响） |
| 论坛 SQLite（帖子/评论/关注） | **世界状态 / 环境** | ①✓ ②✗（影响别人但不归某个人所有） |
| Zep 关系网图谱 | **外部档案 / 知识库** | ①✓ ②✗（模拟中的 agent 读不到它） |

更准确的说法：**系统有"四层跨时间状态"，不是一个统一的记忆架构；真正
"记忆→影响行为"的闭环只有对话历史这一条，而且它进程一停就丢。**

用户的表述里有两处需要温和纠正（下次别顺着他说）：
- 他把"人设"当成第二层 —— 实际上**第二层是对话历史，人设是第四层**。
- 他说"第三层动作用来更新图谱"只对一半：动作**先写进 SQLite 世界**，再被誊抄进图谱；
  誊抄是单向的，图谱从不回流到模拟。

"既是流程又是存储"的双重身份解释（用户困惑的根源）：
流程视角关心"数据怎么变"，状态视角关心"变了之后谁还记得、会不会影响下一步"。
同一份东西两副面孔，所以看起来像在给流程贴记忆标签。
