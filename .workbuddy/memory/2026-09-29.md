## 本体 result 的数据结构（用户贴出真实生成结果后核对）

`ontology_generator.generate()` 返回的 `result` 是三层字典，落进 `project.json` 的 `ontology` 字段：

```
result
├─ entity_types[]  最多 10（末两位强制 Person/Organization 兜底）
│   ├─ name        PascalCase 英文（中文名会被 _to_pascal_case 吃成 Unknown 后静默丢弃）
│   ├─ description 跟随界面语言，可中文
│   ├─ attributes[] 1~10，元素 {name, type, description}；空则补 details 兜底
│   └─ examples[]  真实样例名
├─ edge_types[]   6~10
│   ├─ name        UPPER_SNAKE
│   ├─ description
│   ├─ source_targets[]  {source, target}，引用实体 name，去重，最多 10
│   └─ attributes[]
└─ analysis_summary  模型自我解释
```

### 两个新确认的事实（之前没记过）

1. **attributes 的 `type` 字段是被忽略的**。`graph_builder.set_ontology:349/375` 动态造
   Pydantic 类时，实体属性一律 `Optional[EntityText]`、边属性一律 `Optional[str]`，
   **不读 `type`**。所以 LLM 写 `"type": "integer"`（如 founding_year）只存在于本地 json，
   到 Zep 那边仍是文本。改属性类型必须改 graph_builder，不是改提示词。
2. **`examples` 不上传 Zep**。全项目只有两处消费：
   `simulation_config_generator.py:662`（拼进配置生成的提示词，每类取 3 个）
   和前端 `Step1GraphBuild.vue:55`（展示）。`set_ontology` 完全不读它。

### 接口返回 vs 落盘：两个不一致（新发现）

`POST /api/graph/ontology/generate` 返回的 `data` 只有 6 个字段，但 `project.json` 有 17 个键。
两处容易踩：

1. **`project.ontology` 比 `generate()` 返回值少一个键**。`api/graph.py:372-375` 只存
   `entity_types` + `edge_types`，`analysis_summary` 被单独提出存成
   `project.analysis_summary`（`:376`）。所以**磁盘上的 ontology 里没有 analysis_summary**，
   它跟 ontology 是平级字段。后续读本体时按两个字段取，别只取 ontology。
2. **`files` 元素实际只有 `{filename, size}`**。`models/project.py:36` 的注释写的是
   `[{filename, path, size}]`，**path 从来没写进去**（真实样本已验证）。文件在磁盘上的
   存储名是 hash（如 `files/0da57887.md`），跟 `filename`（原始名）不是一回事。

真实样本（最新一次星尘跑批）：`proj_2749d118b59a`，`total_text_length=4463`，
files=[{filename: 星尘科技开源模型争议.md, size: 9952}]。
