## 讲解：系统记忆机制全景（08:50）

用户问"该系统的记忆机制是什么"。核实后结论是：**系统有 4 层记忆，彼此不通，
且模拟中的 Agent 从不读图谱**（scripts/*.py 完全不 import zep，仅 `debug_pipeline.py` 有读）。

| 层 | 内容 | 载体 | 生命周期 |
|---|---|---|---|
| L1 长期事实 | Zep 时序图谱（episode → node.summary + 带时间的事实边） | Zep 云端 | 永久 |
| L2 短期对话 | camel `ChatHistoryMemory` | 模拟进程内存 | 进程结束即丢 |
| L3 世界状态 | 帖子/用户/关系 SQLite | `uploads/simulations/*_simulation.db` | 永久 |
| L4 静态人设 | system_message ← UserInfo.profile | CSV/JSON + 进程内 | 静态不变 |

### 本次新查证的代码事实（之前没写过的）

- **L2 默认无窗口限制**：`SocialAgent.__init__` 未传 `message_window_size`
  （`oasis/social_agent/agent.py:110` 的 `super().__init__` 调用里没有该参数）
  → camel `ChatHistoryMemory(window_size=None)` = 取全部历史
  （`camel/memories/agent_memories.py:45`），但由 `ScoreBasedContextCreator`
  （`camel/agents/chat_agent.py:478`）按 model token_limit 裁剪 → **超限就丢最旧的，Agent 会"忘事"**。
- **L2 存储是内存**：`ChatHistoryMemory` 的 storage 默认 `InMemoryKeyValueStorage`
  → 进程没了记忆就没了。`scripts/run_parallel_simulation.py` 里**没有**
  `load_memory` / `save_memory` / `resume` / `checkpoint` 任何一处 → 模拟中断只能重跑，且重跑后 Agent 失忆（但世界里帖子还在）。
- **采访默认不进记忆**：`perform_interview`(`oasis/social_agent/agent.py:201`) 的写记忆分支受
  `self.interview_record` 控制，而 `agents_generator.py` 构造 SocialAgent 时从不传该参数 → 默认 False。
  所以第 4 步报告采访 Agent 不会污染它的对话记忆。
- **recsys 是 L3 → L2 的唯一通道**：`agent_environment.py:56 get_posts_env` 调 `self.action.refresh()`
  拿推荐帖子；`get_followers_env`(:64) / `get_follows_env` 直连 sqlite 查 `user` 表。
  我们的 `oasis_recsys_patch.py` 改的就是这条通道。
- **报告怎么"回忆"**：`zep_tools.get_simulation_context:888` = search_graph + 图谱统计 +
  全量节点过滤（`custom_labels` 非 Entity/Node），返回 related_facts/entities。
  这也是第 2 步生成人设时读图谱的入口。

### 可给的改进判断（用户没要求实现）
想让"记忆真正影响行为"必须给 L1→L2 打通（每个 Agent 轮询 Zep 拿与自己相关的事实），
但成本高（N agents × R rounds 次检索）。低成本替代：只在关键轮次（如每 5 轮）批量注入一次。

## 讲解：图谱的作用 —— 边到底有没有用（09:00）

用户问"我知道 agent 是图谱节点生成的，边和关系起什么作用了吗"。核实结论：

**点 = 演员名单，边 = 人物小传 + 报告的证据。边完全不参与模拟过程本身。**

### 边确实起作用的 3 处
1. **人设生成**：`oasis_profile_generator._build_entity_context:457` 的第二段即 related_edges
   （:479-496，含 direction/edge_name/fact），拼成 "### 相关事实和关系" → 注入 prompt(:742)。
   **坑：`context[:3000]`（:732）硬截断**，且拼接顺序是 实体属性 → 相关事实关系 → 关联实体 →
   Zep 检索事实，**关系多的实体会把后面的关联实体信息挤掉**。
   开关在 `simulation_manager.py:299 enrich_with_edges=True`（True 是默认值，可关）。
2. **报告三件套几乎全吃边**：
   - `search_graph:501-524`：facts 主体就是 `edge.fact`（节点只贡献 summary）
   - `panorama_search:1145+`：`active_facts` vs `historical_facts` **全都是边**，
     靠 `invalid_at/expired_at` 二分 → 报告里"演变过程"这一章 100% 依赖边
   - `get_entity_summary:843` 深挖单个节点的边
3. `interview_agents` 基于上面这些实体上下文。

### 边被忽略的地方（重要，别以为到处都用）
- `_summarize_entities`（`simulation_config_generator.py:410`）只输出 **名字 + summary 截断**，
  hot_topics / initial_posts 的生成完全不知道谁和谁有仇。
- `_generate_agent_config_by_rule:910` 只看 **entity_type 字符串**（机构/媒体/专家/学生的
  一堆 hardcode 作息表）→ "关系密切就该多互动"这件事在系统里不存在。
- **社交网络不是从图谱来的**：`_save_twitter_csv:1139` 表头只有 5 列
  （user_id / name / username / user_char / description），没有 follows 列
  → OASIS 的关注关系从 0 起，靠模拟自己长出来。
- 模拟脚本零 zep 引用（见上节）→ Agent 决策时不查图谱。

### 一句话定位
图谱是「开场设定 + 事后分析」的存储，不是「运行时的大脑」。
想让边影响模拟，最小改动是在 `simulation_config_generator` 里用 `related_edges` 生成初始 follows 种子，
但 OASIS 的 CSV 格式不支持 → 得走 IPC 插入动作或改 profiles 加载侧。

## 讲解：OASIS 是什么 + 模拟全过程（09:05）

### OASIS 的定位
`camel-oasis 0.2.5`（CAMEL-AI）装在 site-packages，**不是本项目代码**。
它提供三样东西：`SocialAgent`（继承 camel ChatAgent 的社交智能体）、
`OasisEnv`（= `oasis.make`，管一轮并发调度）、`Platform`（SQLite + Channel + 推荐系统的"物理引擎"）。
MiroFish 自己写的是**外围编排**（起进程、开 sqlite、轮次、过滤活跃 agent、写日志），
真正的"每个 agent 怎么想怎么动"在 OASIS/camel 里。

### 一次模拟的完整链路（已逐段核对）
1. 主进程 `simulation_runner.py:598 subprocess.Popen` 起 `scripts/run_parallel_simulation.py`；
   单 platform 用 `--twitter-only` / `--reddit-only`。
2. `main():1492` → `asyncio.gather` 并行跑两平台；`run_twitter_simulation:1101`。
3. 建环境：`generate_twitter_agent_graph`(读 `twitter_profiles.csv`) →
   `oasis.make(...)`(:1143，`semaphore=30` 限并发) → `env.reset()`(:1149，起 platform 协程 + 注册 agent)。
   **旧库删重建**：db 存在就 `os.remove`(:1140)。
   ⚠️ `oasis/environment/env.py:81` 硬编码 `recsys_type="twhin-bert"`（我们 patch 的点）。
4. 第 0 轮：`event_config.initial_posts` 用 `ManualAction(CREATE_POST)` 一次性 `env.step`(:1156-1178)。
5. 主循环 `round 1..N`：`total_rounds = total_hours*60 // minutes_per_round`（默认 72h / 30min = 144 轮）；
   每轮 `get_active_agents_for_round:1040` 按 **active_hours + activity_level 随机抽样**，
   target 数 = uniform(5,20) × 高峰倍数（peak 1.5 / 凌晨 0.3）；
   然后 `actions = {agent: LLMAction()}` → `env.step`。
6. `OasisEnv.step`（`env.py:135`）一次调用干三件事：
   `update_rec_table()` 刷推荐 → 对每个 agent `_perform_llm_action`（受 semaphore 限流）→ `asyncio.gather` 并发。
   Agent 内部（`agent.py:126`）：`env.to_text_prompt()` 拼观察 → `astep` → camel 自动执行 tool_call →
   动作经 Channel 被 `Platform.running()` 消费 → 写 SQLite（post/like/follow/comment 表）。
7. 每轮结束后 `fetch_new_actions_from_db:657`（按 **rowid** 增量，不是 created_at）把真实动作捞回来，
   `enrich` 补上下文 → 写 `twitter/actions.jsonl`。
8. 主进程 tail 这个 jsonl（`simulation_runner:952`）→ `graph_updater.add_activity_from_dict` → Zep。
9. 轮次跑完**进程不退出**：`wait_for_commands = not args.no_wait`，进 IPC 命令循环响应
   interview / batch_interview / close_env（`ParallelIPCHandler.process_commands:560`）。
   → 这也是报告必须靠 `_ensure_graph_ingestion` 主动排空的原因（父进程等的"进程退出"永远不会来）。

### 两个数字值得记
- `semaphore=30`（`run_parallel_simulation.py:1144`）：并发 LLM 请求上限，改大容易把 API 打挂。
- `refresh_rec_post_count=2, max_rec_post_len=2, following_post_count=3`（`env.py:82-84`）：
  **twitter 每轮每个 agent 只看 2 条推荐帖** —— 视野非常窄，这也是舆情传播慢的原因之一。

## 讲解：OASIS 是不是独立的 + 它的输入输出（11:15）

### 独立性（三句话）
- **不是本项目代码**：`camel-oasis==0.2.5`（`requirements.txt:22`，dist-info 在 `.venv/.../site-packages`），
  CAMEL-AI 出品，git 里没有它，pip 装的。
- **单独能跑**：`oasis.make(agent_graph, platform, database_path, semaphore)` 是公开入口，
  自带 `data/social_media.db` 示例库；但**没有数据就是空壳**——它不会自己找资料、不会造人、不会写报告。
- **它是"引擎"不是"系统"**：类比 Unity 之于游戏——引擎通用可换，剧本/角色/关卡是本项目写的。

### 输入（项目喂给 OASIS 的东西，全部由项目侧准备）
| 输入 | 谁产出 | 说明 |
|---|---|---|
| 人设名单（twitter_profiles.csv / reddit_profiles.json） | `oasis_profile_generator` | 谁登场、什么性格 |
| 模型接口（base_url / key / model）+ `semaphore=30` | config | 每个决定去问谁 |
| 数据库路径 `*_simulation.db` | 脚本 | 世界开在哪（**旧库直接删重建**） |
| 每轮调度指令（谁醒着、跑几轮、并发上限） | `run_parallel_simulation.py` | 不是一次性输入，是**每轮从外面指挥** |

**图谱不在输入里**：OASIS 完全不知道 Zep 存在（scripts 零 zep 引用）。

### 输出（OASIS 吐出来的）
- **SQLite 世界**：`oasis/social_platform/schema/` 下 16 张表 —— user / post / comment / like /
  dislike / follow / mute / rec / trace / report / product / chat_group ...
- **trace 表 = 流水账**：每个动作一条（含 `action` 类型 + `info` JSON）。
  项目用 `fetch_new_actions_from_db:657` 按 **rowid** 增量捞 → 写 `twitter/actions.jsonl`（由 `scripts/action_logger.py:36` 落盘）。
- **采访回答也落在 trace**（`ActionType.INTERVIEW`），`_get_interview_result:517` 再读出来。

### 独立性带来的两个后果
- 好处：社交规则、推荐分发、并发调度都不用自研。
- 坏处：想改它内部行为只能 **monkey-patch**（源码在 site-packages，pip 升级会覆盖），
  且升级版本会冲掉我们的 `oasis_message_patch` / `oasis_recsys_patch`。

### 合成版：`test_scenarios/星尘科技_原始素材合集.md`（5352 字，用户要求"合成一个"）
生成脚本 `test_scenarios/_merge.py`（可重跑）。做法不只是拼接：
1. **按发布日期排序**而非文件名顺序（03-18 → 05-06 → 05-09 → 06-14 → 07-08 → 09-16），
   更像真实检索结果的时间序列，也让 Zep 的时序边有意义；
2. 每篇开头写 `=== 素材 N/6 | 来源方（类型）| 日期 | 作者 ===`；
3. **篇内每累计 360 字补一行 `（以上及以下均出自：素材 N · 来源方 · 日期）`**
   —— 这是解决"切块丢来源头"的关键，阈值取略小于切块长度 500。

**实测带源率对比**（`split_text_into_chunks(500, 50)`）：

| 上传方式 | 切块数 | 带来源线索的块 |
|---|---|---|
| 6 个文件分别上传 | 11 | 6（55%）|
| 单文件、不补标记 | 11 | ~1（只首块）|
| **单文件 + 篇内补标记** | **13** | **13（100%）** |

→ 验证了笔记里"证据驱动分块（每块自带证据头）"的方案有效，且**不依赖改后端代码**。
下一步若要做 P0 的 `created_at`，可照此思路在切块函数里注入证据头 + 时间。
